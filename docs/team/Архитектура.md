# AI-классификатор КТРУ — архитектура и требования

Oct 25, 2026 · сводка по репозиторию github.com/Leshyyyy/ktru (ветки `dev` и `feat/frontend-mock`)

Документ собирает в одном месте то, что уже решено в `docs/analytics/` и `contracts/`. **Источник правды — контракты** (`openapi.yaml`, `schema.sql`, `ml_contracts.py`): если текст здесь расходится с ними, верны контракты.

## Обзор

Система принимает спецификацию товаров (xlsx, csv, pdf), предлагает сопоставление колонок, асинхронно извлекает из каждой строки атрибуты (наименование, бренд, модель, характеристики, количество, единица) и подбирает код КТРУ: топ-3 варианта, уверенность в процентах, пояснение и сверку характеристик. Человек проверяет спорные позиции, правит код через поиск по каталогу и выгружает файл.

**Пользователь** один тип: специалист по закупкам. Авторизации нет — организаторы её не требуют, все данные видны всем (решение в разделе 14 аналитики).

**Ключевые решения**

| Решение | Выбор | Зачем |
| --- | --- | --- |
| Структура входного файла | Не угадываем молча: предлагаем роли колонок, пользователь подтверждает; раскладка запоминается по хешу заголовков | Реальные спецификации с произвольными заголовками не ломают обработку |
| Обработка | API отвечает 202 сразу; задача режется на пачки по 50 позиций, каждая пачка — Celery-задача в очереди `ml` | Нет 504, сбой пачки не останавливает задачу |
| ML | Один метод `Pipeline.classify_batch`, внутри 5 заменяемых компонентов; бэкенд с первого дня работает на `StubPipeline` | Бэкенд, фронт и ML не ждут друг друга |
| Подбор кода | Гибридный поиск (pgvector + trigram/полнотекст + подтверждённые примеры) → быстрый путь, если уверены; иначе реранкер | Укладываемся в 240 с на 1000 позиций на CPU |
| Уверенность | Калиброванная вероятность, что код верный (ECE ≤ 0,05); зоны green ≥ 0,85, yellow ≥ 0,50, red ниже; пороги в `/config` | Процент на экране честный, цвет считает бэкенд |
| Итоговый ответ | Последнее решение пользователя, иначе предсказание rank = 1 — одно правило в представлении `v_item_final` | Правки не теряются, top-3 и история считаются корректно |
| Обратная связь | Исправления пишутся в `confirmed_examples` и используются как кэш точных совпадений | Система не повторяет исправленную ошибку |
| LLM | Необязательна: OpenAI-совместимый endpoint по переменным окружения; без неё — режим `degraded` (правила + cross-encoder) | `docker-compose up --build` работает без ключей и GPU |
| Каталог | Снимок КТРУ с версией, импорт JSONL через `POST /catalog/import`; версия фиксируется в задаче при старте | Обновление без передеплоя, идущие задачи не ломаются |

## Архитектура

```
 браузер ─► frontend (nginx, SPA) ─► api (FastAPI, /api/v1) ──► postgres + pgvector + pg_trgm
                                        │ 202 + job_id                ▲
                                        ▼                             │
                                      redis ──► worker-io  (очередь io: разбор, экспорт, импорт каталога)
                                        │   └─► worker-ml  (очередь ml: Pipeline, модели в памяти) ──► llm (опционально)
                                        └────── beat (раз в минуту watchdog)
 Разовый контейнер migrate: миграции, сиды, загрузка каталога с готовыми эмбеддингами — остальные ждут его.
```

| Сервис | Что внутри | Профиль compose |
| --- | --- | --- |
| `frontend` | SPA за nginx, проксирует `/api/` в `api:8000`, `client_max_body_size` выше 50 МБ | по умолчанию |
| `api` | FastAPI, ничего тяжёлого не считает | по умолчанию |
| `worker-io` | Celery, очередь `io`: разбор файлов, экспорт, импорт каталога, watchdog | по умолчанию |
| `worker-ml` | Celery, очередь `ml`: `Pipeline`, модели загружены один раз | по умолчанию |
| `beat` | Celery beat | по умолчанию |
| `postgres` | Postgres 16 + pgvector + pg\_trgm, тег образа зафиксирован | по умолчанию |
| `redis` | Брокер Celery | по умолчанию |
| `migrate` | Миграции и сиды, завершается | по умолчанию |
| `llm` | Локальный OpenAI-совместимый сервер | `gpu` или `llm` |
| `mock` | Prism по `openapi.yaml` | `mock` |

Тома: `pgdata`, `uploads`, `models`.

### API

Префикс `/api/v1`, полностью — `contracts/openapi.yaml`.

| Группа | Метод и путь | Что делает |
| --- | --- | --- |
| Файлы | `POST /files` | Загрузка, листы, предпросмотр 10 строк, предложенные роли колонок, `layout_hint`, `duplicate_of_job_id` |
| Задачи | `POST /jobs`, `GET /jobs`, `GET /jobs/{id}` | Создание (202), список, статус и прогресс (опрос раз в 1–2 с) |
| Задачи | `POST /jobs/{id}/cancel`, `DELETE /jobs/{id}` | Отмена, удаление |
| Результаты | `GET /jobs/{id}/items` | Позиции с топ-3; фильтры `band`, `status`, `q`, `flag`, `group_id`; сортировка `row_index` / `confidence_asc` |
| Результаты | `POST /jobs/{id}/confirm-bulk` | Подтвердить всё не ниже порога (`skip_flagged` по умолчанию) |
| Результаты | `GET /jobs/{id}/export?format=source\|xlsx\|csv\|json` | Выгрузка, заголовок `X-Unreviewed-Count` |
| Позиции | `GET /items/{id}`, `POST /items/{id}/confirm`, `PUT /items/{id}/decision` | Карточка, подтверждение, ручной код |
| Быстрый режим | `POST /classify` | Синхронно до 20 текстов |
| Каталог | `GET /catalog/search`, `GET /catalog/items/{code}`, `GET /catalog/versions`, `POST /catalog/import` | Поиск для ручной правки, позиция, версии, импорт без передеплоя |
| Качество | `POST /quality/run`, `GET /quality/latest`, `GET /stats` | Оценка на размеченном наборе, мини-дашборд |
| Система | `GET /health`, `GET /config` | Готовность компонентов; пороги, лимиты, режим |

## Конвейер на примере задачи

Пример: `Спецификация_оргтехника.xlsx`, 1000 позиций, CPU, без LLM. Бюджет из раздела 7 аналитики — цель 240 с при лимите 300 с.

| # | Этап | Где | Что происходит | Бюджет |
| --- | --- | --- | --- | --- |
| 1 | Загрузка | `POST /files` | Тип по содержимому, лимиты, листы, предпросмотр, роли колонок; PDF — только первые 3 страницы | < 2 с |
| 2 | Подтверждение колонок | Пользователь → `POST /jobs` | Ровно одна колонка `name`; 202 сразу | < 1 с |
| 3 | Разбор | `parse_file` / io | Строки в `items`, пропуск пустых и «Итого», `raw_text` = name + description + characteristics; нарезка на пачки | 10 с |
| 4 | Атрибуты | `process_chunk` / ml | Правила для большинства, LLM пачками по 20 только для сложных (если включена) | 60 с |
| 5 | Эмбеддинги | ml | Пачки по 64, дедупликация одинаковых строк по `normalize_text` | 40 с |
| 6 | Поиск | ml | HNSW + trigram, топ-20, слияние, подтверждённые примеры | 30 с |
| 7 | Маршрутизация и реранкер | ml | Быстрый путь, если `top1_fused ≥ 0,75` и отрыв ≥ 0,15; иначе реранкер (цель ≤ 20% позиций) | 80 с |
| 8 | Калибровка и запись | ml | Уверенность по признакам, топ-3, сверка характеристик, флаги, пачковая вставка | 10 с |
| 9 | Финал | `maybe_finalize` / io | `done` или `done_with_errors`, счётчики `summary` | < 1 с |
