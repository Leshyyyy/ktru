# 13. Открытые вопросы и риски

Четыре вопроса организаторам меняют архитектуру, а не детали; отправить их нужно в первый же день (контакт — в презентации кейса). До ответа работаем по допущениям раздела 1.

| № | Вопрос | Что меняется от ответа |
| --- | --- | --- |
| 1 | Точность считается по полному коду КТРУ или только по ОКПД2? | Метрика, сложность поиска, разметка |
| 2 | Будут ли переданы каталог КТРУ и тестовый набор? В каком формате? | Весь раздел 9 |
| 3 | Какой LLM разрешён и будут ли ключи? Можно ли внешние API? | Режимы в разделе 7 |
| 4 | На каком железе запускают проект проверяющие (CPU, ОЗУ, GPU)? | Размер моделей, бюджет времени |

**Риски**

| Риск | Вероятность | Что делаем |
| --- | --- | --- |
| Каталог КТРУ неудобно выгрузить целиком | Высокая | День 1: выяснить способ. Резерв: частичный каталог по нужным классам ОКПД2 и честная пометка в README |
| 1000 позиций не укладываются в 5 минут на CPU | Средняя | Замер в неделе 1, каскад fast / rerank, батчинг, лёгкий режим моделей |
| Не добираем 85% на реальных данных | Средняя | Добавляем подтверждённые примеры, сверку характеристик, дообучение на GPU; в крайнем случае честно говорим об этом и показываем top-3 |
| Поиск по HNSW с фильтром по версии каталога возвращает меньше кандидатов, когда в базе больше одной версии | Средняя | pgvector ≥ 0.8 и `SET hnsw.iterative_scan = relaxed_order` в сессии поиска; либо хранить векторы только у актуальной версии. Подробно — в комментарии к `schema.sql` |
| Сборка на arm64 ломается из-за зависимостей | Средняя | День 2: проверить сборку всех образов на обеих архитектурах |
| Разметка задерживается | Высокая | Разметка начинается в день 1, большая модель даёт предразметку, люди проверяют |
| Тексты из спецификаций пытаются «управлять» LLM (prompt injection) | Низкая | Текст позиции обёрнут в разделители и помечен как данные; вывод проверяется по JSON-схеме и код должен быть в каталоге |
