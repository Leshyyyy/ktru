Контракты (`openapi.yaml`, `schema.sql`, `ml_contracts.py`, заглушка) уже обновлены.

**Отложено** (вернёмся, если останется время)

- №5, версионирование каталога со статусами: оставляем ручной `POST /catalog/import`. В схему добавлены `catalog_items.status` и `replaced_by`, предупреждение `archived_code` включаем, если поле есть в выгрузке. Автоскачивание не делаем: условия использования и сеть у проверяющих под вопросом.
- №6, аудит-лог: расширили `decisions` полями `old_code` и `reason` (причина необязательна). Хеш-цепочка и права «только INSERT» не нужны.

**Отклонено**

- №10, API-ключи, webhook, HMAC, лимиты: не входит в критерии, REST уже есть.
- №12, сопоставление с прайсом: отдельная задача.
- №14, роли, `org_id`, RLS, JWT, квоты: противоречит допущению «без авторизации» и усложняет `docker-compose up`.

**Что остаётся нашим из схемы:** модель «предсказания (топ-3) + решения + итоговое представление», а не плоские `items.ktru_code` и `confidence`: без топ-3 и истории решений нельзя считать top-3 и нельзя корректно исправлять. Названия таблиц каталога остаются `catalog_*`.

**Риск:** пункты 4 и 5 зависят от формата реальной выгрузки КТРУ, которую никто пока не видел. Получить выгрузку нужно в первую неделю.

## 14.1. Правки по ревью контрактов от 8 октября

Бэкендер прислал разбор `contracts_review.md`. Принято и внесено в контракты (проверки: валидатор OpenAPI, 48 примеров без ошибок, схема БД применяется на Postgres 16, заглушка прогнана на 1000 позиций):

| № | Что исправлено | Где |
| --- | --- | --- |
| 2.1 | Уверенность не растёт с рангом. В заглушке второй код больше не бывает увереннее первого. Бэкенд проверяет порядок при приёме ответа ML | `ml_contracts.py`, `stub_pipeline.py` |
| 2.2 | Ключ группы теперь `наименование\|бренд\|модель`. Принтер и картридж к нему больше не склеиваются. Конвейер объединяет только позиции с одинаковым нормализованным текстом | `ml_contracts.py`, `schema.sql`, заглушка |
| 2.3 | `group_id` ставится всегда, когда есть ключ; `group_size` считается при выдаче; API отдаёт `group_id = null` при размере группы 1 | `schema.sql`, `openapi.yaml` |
| 2.4 | `decisions.via` = `manual` или `bulk`. Массовые подтверждения не пишут эталонные примеры и не входят в метрику | `schema.sql`, `openapi.yaml` |
| 2.5 | `green_correction_rate` = исправленные / (подтверждённые вручную + исправленные) среди зелёных, проверенных человеком | `openapi.yaml` |

| 2.8 | Схема строки каталога `CatalogRow` и интерфейс `CatalogIndexer` (эмбеддинги версии каталога и примеров) | `openapi.yaml`, `ml_contracts.py` |

| 2.10 | `items.processed_at` для ETA, скорости и времени ошибок | `schema.sql` |

Из мелочей внесено: экспорт отменённой задачи разрешён (выгружается обработанное); в xlsx все значения пишутся строковыми ячейками, апостроф нужен только в csv; удаление задачи во время обработки описано; watchdog ловит `queued`, `parsing` и `processing`, Redis с AOF; чтение xlsx и xls через python-calamine; лимит nginx выше 50 МБ при проверке 50 МБ в приложении; CORS `expose_headers` для `X-Unreviewed-Count` и `Content-Disposition`; пояснено различие `max_rows` и `max_items_per_job`.

**Не принято без обсуждения:** статус `needs_review` для зелёных позиций с предупреждениями. Логика разумная, но меняет счётчики зелёных и поведение массового подтверждения; решаем вместе с фронтендом. Сейчас такие позиции остаются `processed`, а `confirm-bulk` их пропускает по умолчанию (`skip_flagged`).

**Для критерия 7 (запуск `docker-compose up --build`):** миграции и сиды выполняет разовый контейнер `migrate`, остальные сервисы его ждут; модели кладутся в образ на этапе сборки; эмбеддинги каталога поставляются готовыми, а не считаются при первом старте; в репозитории лежит `.env.example`, без ключей LLM система работает в режиме `degraded`.
