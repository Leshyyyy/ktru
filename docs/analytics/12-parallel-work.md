# 12. Работа в параллель

Три команды связаны только тремя файлами-контрактами, и каждая может работать со второго дня, не дожидаясь других. Эти три файла живут в папке `contracts/` репозитория.

| Файл | Кто с кем связан | Чем пользуется каждая сторона |
| --- | --- | --- |
| `openapi.yaml` | Фронт ↔ бэкенд | Фронт генерирует типы и поднимает мок-сервер; бэкенд сверяет с ним ответы |
| `ml_contracts.py` | Бэкенд ↔ ML | Бэкенд вызывает `Pipeline` и работает с `StubPipeline`; ML реализует те же интерфейсы |
| `schema.sql` | Бэкенд ↔ ML (данные) | Бэкенд владеет таблицами обработки; ML — `catalog_items`, `confirmed_examples`, `eval_*` |

Рядом лежит заглушка `contracts/stub_pipeline.py`: детерминированные ответы с вымышленными кодами (префикс 99.99), примерно 60% зелёных, 25% жёлтых и 15% красных позиций. Текст `__fail__` в позиции имитирует сбой, а `STUB_DEGRADED=1` — режим без LLM.

**Что делает каждый в первый день, не дожидаясь других**

- **Фронт:** `npx @stoplight/prism-cli mock contracts/openapi.yaml` — и весь интерфейс можно разрабатывать на примерах из контракта. Примеры в файле намеренно реалистичные: есть зелёные, жёлтые и красные позиции, ошибки и частичный прогресс.
- **Бэкенд:** поднимает сервис с `StubPipeline`, который возвращает детерминированные ответы по хэшу текста и имитирует задержку. Так очереди, прогресс и экспорт работают до появления настоящего ML.
- **ML:** работает автономно, без бэкенда, через CLI: `python -m ml.evaluate --split dev` читает JSONL-разметку и пишет метрики. База нужна только для поиска по каталогу, она поднимается из `schema.sql` одной командой.

**Правила изменения контрактов**

1. Меняется только через отдельный pull request в `contracts/` с одобрением обеих сторон.
2. Добавление необязательных полей — в любое время. Удаление и переименование полей после конца недели 1 — только по общему решению.
3. В CI есть тест, который сверяет ответы бэкенда с `openapi.yaml`, а `StubPipeline` — с типами из `ml_contracts.py`.

**Что делает каждая роль по неделям** (неделя 1 — 5–11 октября, 2 — 12–18, 3 — 19–25, 4 — 26 октября — 1 ноября)

| Роль | Неделя 1 | Неделя 2 | Неделя 3 | Неделя 4 |
| --- | --- | --- | --- | --- |
| Бэкенд | Скелет FastAPI, Alembic по `schema.sql`, `/files`, `/jobs`, `/health`, `StubPipeline` | Разбор xlsx/csv/pdf, Celery-пачки, прогресс, экспорт, `/catalog/import` | Правки и подтверждения, `confirmed_examples`, `/quality`, замер 1000 позиций | Баги, README с примерами API |
| Фронтенд | Макеты 4 экранов, приложение на моке, экран загрузки и колонок | Список задач, прогресс, таблица результатов с фильтрами | Карточка позиции, правка с автодополнением, массовое подтверждение, экспорт, страница качества | Пустые и ошибочные состояния, полировка |
| ML: поиск | Выбор модели эмбеддингов, импорт каталога, гибридный поиск, первый замер | Реранкер, маршрутизация fast / rerank, подключение к `Pipeline` вместо заглушки | Калибровка уверенности, подтверждённые примеры, настройка порогов на `dev` | Финальный замер на `test` |
| ML: атрибуты | Правила для бренда, модели и единиц; JSON-схема для LLM; замер на `attrs` | LLM-путь пачками, режим без LLM | Доведение до ≥ 90%, пояснения, сверка характеристик с КТРУ | Помощь с видео и демо |
| Данные и DevOps | Выгрузка КТРУ, разметка первых 100, CI, вопросы организаторам | Разметка до 300, заморозка `dev` / `test`, тестовые файлы на 100 и 1000 строк | Замер скорости на слабом железе, сценарий демо | Чистый запуск на amd64 и arm64, видео |
