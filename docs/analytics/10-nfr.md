# 10. Нефункциональные требования

Главное нефункциональное требование — проект должен запускаться у проверяющего одной командой `docker-compose up --build` без ручных шагов и без ключей. Остальное подчинено этому.

| Область | Требование |
| --- | --- |
| Запуск | Одна команда. Веса моделей и данные каталога подтягиваются при первом старте в отдельный том; повторный запуск быстрый. README честно пишет, сколько времени и места нужно на первый старт. |
| Режимы | `docker-compose up --build` — CPU-режим. `docker-compose --profile gpu up --build` — GPU-режим (большая модель). Оба режима должны работать на `linux/amd64` и `linux/arm64`. |
| Готовность | `GET /health` возвращает состояние базы, очереди, моделей и каталога по отдельности. Фронт показывает «система готовится», пока `ready` ложно. |
| Производительность | 1000 позиций ≤ 240 с. Одна позиция через `POST /classify` ≤ 3 с. Таблица результатов открывается ≤ 1 с на 1000 строк (пагинация на сервере). |
| Надёжность | Падение воркера во время задачи не теряет данные: `watchdog` перезапускает необработанные позиции, идемпотентность не даёт дублей. |
| Загрузка файлов | nginx перед API по умолчанию пропускает тело запроса до 1 МБ. Нужно `client_max_body_size 50m`, иначе любой файл больше 1 МБ получит 413 от nginx в его собственном формате. Таймаут прокси — не меньше 60 с. |
| База | Образ Postgres с pgvector версии 0.8 или новее (нужен `hnsw.iterative_scan`, см. риски). Версию образа фиксируем тегом, а не `latest`. |
| Конфигурация | Всё через переменные окружения; `.env.example` в репозитории со всеми переменными и комментариями. Секреты не коммитятся. |
| Логи | JSON-логи с `request_id` и `job_id`. Каждая пачка пишет тайминги этапов в `ClassificationResult.timings_ms` — по ним строится бюджет из раздела 7. |
| Безопасность | Валидация типа файла по содержимому, не по расширению. Защита от опасных формул в xlsx/csv (значения, начинающиеся с `=`, `+`, `-`, `@`, экранируются при экспорте). Текст из файла никогда не попадает в промпт LLM как инструкция: он обёрнут в разделители и помечен как данные. |
| Персональные данные | Спецификации закупок обычно их не содержат. В облачном режиме текст позиций уходит во внешний API, поэтому в интерфейсе есть явный индикатор текущего режима. |
| Тесты | Юнит-тесты на парсеры и выбор колонок; энд-ту-энд тест (загрузка → задача → экспорт) на заглушке `StubPipeline`, который входит в CI. |
