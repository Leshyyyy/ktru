# 9. Данные и оценка качества

Для двух критериев приёмки (атрибуты ≥ 90%, классификация ≥ 85%) нужен размеченный набор, которых у организаторов мы не получили. Мы собираем свой и ведём его как отдельный продукт с владельцем.

**Каталог КТРУ**

- Источник — каталог в ЕИС (zakupki.gov.ru). Как именно выгружать его целиком, не проверено — это первая задача данных в день 1. Размер каталога тоже неизвестен, от него зависят время импорта и выбор модели.
- Код КТРУ состоит из кода ОКПД2 и порядкового суффикса (пример формата: `26.20.15.000-00000001`). Мы храним оба поля отдельно.
- Для каждой позиции нужны: наименование, описание, единица измерения и список характеристик с допустимыми значениями. Характеристики нужны для проверки совпадения и объяснения; если в источнике их нет, поле `characteristics` остаётся пустым, а объяснение отключается — без ошибок.
- Формат импорта — JSONL, одна позиция на строку; скрипт преобразует исходную выгрузку в этот формат.

```json
{"ktru_code": "26.20.15.000-00000001", "okpd2_code": "26.20.15.000", "name": "...", "description": "...", "unit": "шт", "characteristics": [{"name": "...", "values": ["..."], "required": true}]}
```

**Размеченный набор**

| Набор | Размер | Для чего | Доступ |
| --- | --- | --- | --- |
| `dev` | 210 позиций | Подбор порогов, калибровка, отладка | Все |
| `test` | 90 позиций | Финальный замер для защиты | Не смотрим и не подбираем под него; запуск — раз в неделю |
| `attrs` | 50 позиций | Точность извлечения атрибутов (наименование, бренд, модель) | Подмножество основных 300 позиций с дополнительной разметкой атрибутов; dev / test — как у них |

Позиции берутся из реальных спецификаций закупок в ЕИС, нужны разные отрасли: IT-оборудование, медицина, канцелярия, хозяйственные товары, стройматериалы. Каждая позиция размечается двумя людьми независимо; расхождения разбираются вместе. Доля трудных позиций (несколько подходящих кодов, грязный текст) — не менее трети.

Формат разметки — JSONL:

```json
{"id": "s-0042", "split": "dev", "raw_text": "Ноутбук Lenovo IdeaPad 3 15IAU7, 15.6\", i5-1235U, 16 ГБ", "expected_ktru_code": "...", "expected_attrs": {"name": "Ноутбук", "brand": "Lenovo", "model": "IdeaPad 3 15IAU7"}, "difficulty": "easy", "source": "ЕИС, закупка ..."}
```

**Метрики**

| Метрика | Как считаем | Цель |
| --- | --- | --- |
| Top-1 accuracy, полный код | доля позиций, где код в первом месте совпал с эталоном | ≥ 85% (критерий организаторов) |
| Top-1 accuracy, уровень ОКПД2 | совпадение части кода до дефиса | ≥ 92% |
| Top-3 accuracy | эталон среди первых трёх | ≥ 95% |
| Точность атрибутов | по полям `name`, `brand`, `model` после нормализации (регистр, пробелы, транслитерация бренда) | ≥ 90% (критерий организаторов) |
| ECE (калибровка) | среднее расхождение заявленной и фактической точности по бинам уверенности | ≤ 0,05 |
| Доля быстрого пути | позиции без реранкера / все позиции | ≥ 80% |
| Время 1000 позиций | стеновое время от старта задачи до `done` | ≤ 240 с (лимит организаторов 300 с) |

Цели сверх критериев организаторов — наши, с запасом на разницу между нашим набором и их закрытым.

**Правила честной оценки**

1. Пороги, промпты и веса подбираются только на `dev`. `test` запускается не чаще раза в неделю, а его позиции не попадают в примеры для промптов и в `confirmed_examples`.
2. Дубли текста между `dev` и `test` запрещены, если товар один и тот же.
3. Каждый прогон оценки сохраняется в `eval_runs` вместе с конфигурацией, чтобы цифры можно было воспроизвести.
4. Результаты в видео и на защите — только с `test`, с указанием размера набора.
