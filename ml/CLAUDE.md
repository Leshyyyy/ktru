# ml/ — подбор кода КТРУ

Владелец — Jove. Бэкенд вызывает только `ml.pipeline.get_pipeline().classify_batch(...)`; интерфейс — `contracts/ml_contracts.py`, его не меняем без PR с одобрением бэкенда.

## Как устроено

| Файл | Что делает |
| --- | --- |
| `pipeline.py` | `KtruPipeline` (реализация `Pipeline`): атрибуты → категории ОКПД2 → кандидаты внутри категорий → сверка характеристик → реранкер для неуверенных → калибровка → топ-3 с пояснениями |
| `category.py` | Ступень 1: топ ОКПД2 по ближайшим соседям среди названий карточек СТЕ (символьные 3–4-граммы + слова, голос близость⁶; `python -m ml.category` строит модель) |
| `ste_eval.py` | Живой проверочный набор категорий из карточек СТЕ (эталон «<ОКПД2>-X», методика Таира) |
| `extract.py` | `RulesExtractor`: наименование, бренд (словарь + эвристика), модель, характеристики «ключ: значение» |
| `values.py` | Разбор значений КТРУ («≥ 17», «> 2.5 и ≤ 3», «от 8 ГБ») и чисел с единицами из текста позиции |
| `charmatch.py` | Сверка характеристик: match / mismatch / missing, привязка к названию характеристики в тексте |
| `retrieve.py` | `MemoryRetriever`: кандидаты внутри категорий ОКПД2 (+ запасные из всего каталога); TF-IDF по наименованию и по наименованию с характеристиками (или эмбеддер) + нечёткое название + обязательные характеристики; кэш подтверждённых примеров |
| `vector_store.py` | Эмбеддинги наименований в Postgres: `catalog_items.embedding` (pgvector, `vector(1024)`, короткие векторы дополняются нулями) |
| `rerank.py` | none / cross_encoder / llm (выбор из кандидатов моделью `LLM_MODEL` через OpenRouter или Jev) |
| `silver.py` | «Серебряная» разметка точного кода живых строк сильной LLM (среди всех позиций ОКПД2 карточки) |
| `calibrate.py` | Калибратор уверенности; `python -m ml.calibrate` обучает на dev |
| `evaluate.py` | Метрики раздела 9 аналитики |
| `synth.py` | Синтетический dev по характеристикам — временная замена ручной разметке |

Главное о данных: внутри одного кода ОКПД2 позиции КТРУ называются одинаково и различаются обязательными числовыми
характеристиками — там решает `charmatch.py`. Но сначала надо попасть в категорию, а по тексту КТРУ это плохо
получается на живых названиях (разбор Таира, 28.10: 40% ОКПД2): медицинские разделы с теми же названиями, случайные
совпадения характеристик. Поэтому схема двухступенчатая: категорию дают карточки СТЕ, где ОКПД2 поставили сами
поставщики, а сверка характеристик выбирает позицию внутри категорий и в чужую категорию не уводит.

## Команды (из корня репозитория)

```bash
python -m pytest ml/tests -q
# модель категорий (данные СТЕ: ste.parquet из dantetemplar/zakupki-dataset, ревизия как в ml/fetch_catalog.py)
python -m ml.ste_eval --ste data/ktru/v2/ste.parquet --catalog data/ktru/v2/catalog_fetched.jsonl --seed 8 --n 1500 \
    --exclude data/ktru/ste/ste_eval_tair.jsonl --out data/ktru/ste/ste_dev.jsonl
python -m ml.category --ste data/ktru/v2/ste.parquet --catalog data/ktru/v2/catalog_fetched.jsonl \
    --exclude data/ktru/ste/ste_eval_tair.jsonl data/ktru/ste/ste_dev.jsonl --out ml/models/category.joblib
KTRU_CATALOG_PATH=data/ktru/v2/catalog_fetched.jsonl python -m ml.calibrate \
    --data data/ktru/v2/eval_samples_v3_dev.jsonl data/ktru/ste/ste_dev.jsonl
KTRU_CATALOG_PATH=data/ktru/v2/catalog_fetched.jsonl python -m ml.evaluate --data data/ktru/v2/eval_samples_v3_dev.jsonl
KTRU_CATALOG_PATH=data/ktru/v2/catalog_fetched.jsonl python -m ml.evaluate --data data/ktru/ste/ste_eval_tair.jsonl \
    [--text-field raw_text_spec]
# test (eval_samples_v3_test.jsonl) — один раз перед сдачей, ничего под него не подбирать
```

Ключи — в `ml/.env` (образец `ml/.env.example`, сам файл в `.gitignore`). `RERANKER=llm` включает Jev через OpenRouter,
ответы кэшируются в `ml/artifacts/llm_cache.jsonl`, повторные прогоны бесплатны.

Скорость — только `classify_batch`, без бэкенда, процесс привязан к 2 ядрам (как в замере Таира); критерий ТЗ < 300 с.
Короткие названия дольше длинных строк: у них низкие оценки поиска, в предотбор попадает больше позиций.

**Весь путь в Docker (28.10):** compose с `PIPELINE=real` (эта ветка + #16 + dev), CSV на 1000 живых строк
(набор Таира: наименование, характеристики, количество, единица) → `POST /files` → `POST /jobs` (0,25 с) → готово
за 101–115 с, ошибок 0. ОКПД2 76,9% — как офлайн. Зоны по порогам `/config`: green 25% (ОКПД2 верен в 94%),
yellow 45% (76%), red 30% (64%). worker-ml готов через ~1 мин после старта, память 1,3 ГБ.

Уверенность на наборе Таира: ≥ 0,7 — у четверти позиций, из них ОКПД2 верен в ~94%; < 0,4 — у ~30%, верен в ~60%.

- Модель категорий (`ml/models/category.joblib`, 48 МБ на диске, 74 МБ в памяти, строится ~40 с): 106 тыс. названий
  СТЕ (≤ 150 на код), 1157 кодов ОКПД2. Сама по себе на ste_dev — 79,9% (топ-3 — 89,6%). Перебор на ste_dev:
  символьные 3–4-граммы, голос близость² — 74,6%; близость⁴ — 77,7%; близость⁶ и 30 соседей — 78,5%; + слова 1–2
  с долей 0,3 — 79,9% (выбрано). Больше названий на код почти не помогает: 300 — +0,6 п., 1000 — 0.
  Без файла модели конвейер ищет по всему каталогу, как раньше.
- Синтетика v3 ниже прежней (85,3 против 87,7% top-1): тексты v3 собраны из текста КТРУ, а 19% их кодов ОКПД2 нет
  среди карточек СТЕ. Размен сознательный: на живых строках +31–35 п. Веса — `retrieve.py` (W_CAT, CAT_POWER, FALLBACK_N).
- Строка начинается с точного наименования позиции КТРУ (≥ 12 символов; 82% строк v3, 12% живых названий) —
  вес категории 0,15 вместо 0,4 (EXACT_W_CAT): v3 top-1 83,1 → 86,4%, живые названия −0,3 п. Вес сверки
  характеристик 0,45 вместо 0,55: v3 +0,2 п., строки с характеристиками +1 п.
- Перебор весов на ste_dev / v3 dev (ОКПД2 названия / с характеристиками / v3 top-1, без калибратора):
  без категорий 40 / 46 / 88,3; новая модель: W_CAT 0,4 — 78,0 / 79,7 / 83,1 (выбрано); 0,3 — 73,3 / 76,7 / 86,1;
  0,5 — 78,3 / 81,0 / 78,7; доля² и W_CAT 0,4 — 75,3 / 77,3 / 84,7.
- Калибратор (`ml/models/calibrator.joblib`) обучен на v3 dev и 315 карточках ste_dev, у ОКПД2 которых одна
  позиция КТРУ (там верный ОКПД2 = верный код). ECE на отложенных половинах 0,041–0,042 (Платт без изотоники —
  0,07–0,11, изотоника по 20 корзинам — 0,045–0,068).
- Сверка характеристик: совпадение только по единице измерения и «да» из одного упоминания слова («принтер» →
  «Принтер: Да») — слабые свидетельства с весом W_WEAK = 0,3. Значения из словаря каталога ищутся одним составным
  выражением на характеристику и запрос (было: каждое значение у каждого кандидата — в 3 раза медленнее, ответы те же).
- **Бренд на реальных названиях СТЕ** (`python -m ml.eval_brands --data data/ktru/v2/ste_attrs_eval.jsonl`): 83,7%
  со словарём марок `ml/models/brands.txt` (30 тыс. марок из СТЕ). На марках, которых нет в словаре, — 58,9%.
- Загрузка полного каталога ~50 с при старте воркера, модели категорий — ещё несколько секунд.

**Порог зелёной зоны (GREEN_THRESHOLD в бэкенде, 29.10).** Точность первого кода выше порога уверенности:

| Порог | v3 dev: доля / любой допустимый | ste_dev (живые с характеристиками): доля / ОКПД2 |
| --- | --- | --- |
| 0,60 | 89% / 95,8% | 51% / 87,2% |
| **0,70** | **71% / 98,8%** | **28% / 92,2%** |
| 0,85 (сейчас) | 61% / 98,8% | 22% / 93,2% |

Рекомендация — GREEN_THRESHOLD = 0,70: точность та же, зелёных на 6–10 п. больше. Позиции с предупреждением
«нет обязательной характеристики» массовое подтверждение и так пропускает (без них при 0,70 — 99,1% / 93,1%).

**Эмбеддинги в ступени категорий (29.10) — не помогли.** e5-small по 106 тыс. названий СТЕ (расчёт 9 мин),
смесь близостей с TF-IDF: на ste_dev 80,0% против 79,9% у одного TF-IDF (топ-3 90,1 против 89,6%); одни
эмбеддинги — 66%. Модель выросла бы на ~80 МБ — не встроено.

**Что ещё пробовали для категории (29.10), всё — без выигрыша, не встроено:**
- значения характеристик «Вид…/Тип…» в запросе (есть у 73% строк): 79,9 → 78,8% — значения слишком общие;
- больше названий на код с отбором «половина самых покупаемых + половина случайных»: 300 — 80,5% (модель 127 МБ),
  600 — 81,1% (212 МБ, файл больше лимита GitHub); 150 — как сейчас. +1 п. не стоит вдвое большей модели.
- Разбор ошибок на ste_dev (302 из 1500): 46% — соседний код того же класса ОКПД2 (пельмени «полуфабрикаты для…»
  против «…замороженные»), заметная доля — спорная разметка поставщиков («Кисть декоративная» с кодом «Ремень»);
  ошибочные ответы почти всегда неуверенные (доля голосов 0,16–0,3) и уходят в жёлтую/красную зону.
  Подход на соседях по СТЕ упёрся в потолок ~80%; дальше — только живая разметка заказчиков (задача Донира).
- Другие модели на тех же 106 тыс. названиях (29.10, ste_dev, ОКПД2 / топ-3): kNN (сейчас) — 79,9 / 89,6%;
  наивный Байес (ComplementNB) — 72,3%; линейная (SGD, modified huber) — 77,5 / 84,8%, смесь с kNN — 80,8%
  (веса 2 ГБ); дообученный e5-small (слои без таблицы словаря, классификатор ОКПД2, 1 эпоха, 70 мин на CPU) —
  66,9 / 79,5%, смесь с kNN — 80,7%. Пять разных моделей дают 77–81%: в названии карточки больше нет сведений.
- Шум разметки — не причина: одинаковые названия СТЕ (302 тыс. карточек) получают один ОКПД2 в 97% случаев.
  Ошибки — новые названия, где соседние коды одного класса по названию не различить.

**Эмбеддинги и pgvector.** `EMBEDDER_MODEL` включает смысловую близость наименований. Векторы считаются по
уникальным наименованиям КТРУ (~13 тыс.); если воркер видит базу (`DATABASE_URL` или `POSTGRES_*`/`APP_DB_*` из
compose), они пишутся в `catalog_items.embedding` (pgvector, `vector(1024)`, короче — дополняются нулями: косинус тот
же) и при следующем старте читаются оттуда, а не пересчитываются. Проверено на `pgvector/pgvector:0.8.2-pg16`:
`load_version` и загрузка из файла (векторы — в последнюю готовую версию каталога). Замеры:

| Модель | ОКПД2 ближайшего наименования, ste_dev | + TF-IDF | 1000 запросов, 2 ядра |
| --- | --- | --- | --- |
| TF-IDF по наименованию | 45,1% | — | — |
| intfloat/multilingual-e5-small (384) | 27,3% | 48,1% | 19 с |
| deepvk/USER-bge-m3 (1024) | 45,6% | 51,7% | 192 с — не укладывается в 300 с с конвейером |

С текущими настройками (точное наименование, вес сверки 0,45) e5-small с весом 0,10 нейтрален или чуть лучше:
ste_dev 77,7 / 81,0% против 77,7 / 80,7%, v3 top-1 87,0% против 86,6%. ТЗ прямо требует эмбеддинги и pgvector,
поэтому **по умолчанию включены** (`EMBEDDER_MODEL=intfloat/multilingual-e5-small`, «-» — выключить). Нужны torch (CPU)
и sentence-transformers в образе; без них конвейер работает на TF-IDF и пишет предупреждение. Первый старт воркера
считает векторы ~15 тыс. наименований (минуты на CPU) порциями прямо в pgvector — перезапуск продолжает с места,
дальше они читаются из базы. Модель (~470 МБ) лучше скачать при сборке образа, а не при первом старте.

**Точный код на живых строках (серебряная разметка, 28.10).** `python -m ml.silver`: карточки СТЕ набора Таира,
модель `anthropic/claude-sonnet-5.5` выбирает подходящие позиции среди ВСЕХ позиций ОКПД2 карточки (не наших
кандидатов); берутся только ответы с высокой уверенностью, ОКПД2 с одной позицией — без модели. Баланс OpenRouter
у команды $10, поэтому размечено 276 строк (209 — одна позиция в ОКПД2, 67 — моделью; высокую уверенность модель
дала в 67 из ~350: в карточках часто нет различающих характеристик). `data/ktru/ste/silver_tair.jsonl`:

| Строка | Точный код | ОКПД2 | top-3 | ECE |
| --- | --- | --- | --- | --- |
| название + характеристики | **73,9%** | 75,7% | 80,4% | 0,075 |
| только название | 70,7% | 74,6% | 75,7% | 0,051 |

Внутри верной категории точный код верен в ~98%: почти все ошибки — категория. Выборка смещена к ОКПД2 с одной
позицией; разметка модельная, не ручная.

**Выбор кода языковой моделью для неуверенных позиций (RERANKER=llm + LLM_MODEL, 28.10)** — не помог.
`ChatChooser`: строка и 5 наших кандидатов с обязательными характеристиками → `{"choice": N}`, выбранный код
получает вес RERANK_WEIGHT. На ste_dev (300, ОКПД2: с характеристиками / названия) и v3 dev (top-1):

| Модель, вес | ste спец. | ste назв. | v3 top-1 |
| --- | --- | --- | --- |
| без LLM | 81,0% | 76,7% | 87,0% |
| claude-haiku-5.5, 0,3 | 81,3% | 77,3% | 87,7% |
| claude-haiku-5.5, 1,0 (решает модель) | 78,7% | 73,3% | 85,9% |
| qwen3.5-flash, 1,0 | 76,0% | 73,0% | 84,9% |

Если верной категории нет среди кандидатов, модель её не найдёт; если есть — поиск и так её выбирает, а модель
иногда предпочитает «по смыслу лучшую» категорию, не совпадающую с разметкой поставщиков. DeepSeek V4 Flash —
~10 с на запрос, в 300 с на 1000 позиций не укладывается. По умолчанию выключено.

**Jev (RERANKER=llm) на старом dev:** с весом 0,25–0,75 исправляет и портит поровну, по умолчанию вес 0,05.
Перепроверить на полном каталоге и живых текстах.

## Грязные строки (проба 31.10, карточка P1-3 ревью)

Полный каталог (снимок Hugging Face), калибратор v3.2 (PR #26), оба режима. Исключений нет. Пусто и пробелы — ошибка
позиции «Пустой текст позиции». Одна буква, эмодзи, нулевой байт, только цифры, код КТРУ, русский с арабским, строка-инъекция:
уверенность 0,08–0,54, ниже зелёной зоны (0,70). 100 тыс. символов — 0,37–0,44, ~10 с на позицию вместо ~1 с;
длину не ограничиваем, размер файла и число строк ограничены раньше.

## Правила

- Источники: каталог КТРУ — открытый датасет ЕИС (жюри разрешило), карточки СТЕ (dantetemplar/zakupki-dataset) —
  Егор разрешил использовать и класть в git (28.10). Обученные артефакты (`ml/models/`: калибратор, марки, модель
  категорий) — в git и в образе. Сырые данные (`data/`) не коммитим из-за размера; в тестах — только
  `contracts/fixtures/` и искусственные строки из `ml/tests/`.
- `eval_test_candidates` и test-разметку не открывать при разработке; пороги и веса — только по dev
  (`eval_samples_v3_dev.jsonl`, `ste_dev.jsonl`). Набор Таира `ste_eval_tair.jsonl` — отложенная проверка, под него не подбирать.
- `ml/` не импортирует FastAPI и Celery.
- Синтетические метрики оптимистичны: веса и калибратор не подбирать на одной синтетике.
- Новая логика — с тестом в `ml/tests/`.
