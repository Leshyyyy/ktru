# ml/ — подбор кода КТРУ

Владелец — Jove. Бэкенд вызывает только `ml.pipeline.get_pipeline().classify_batch(...)`; интерфейс — `contracts/ml_contracts.py`, его не меняем без PR с одобрением бэкенда.

## Как устроено

| Файл | Что делает |
| --- | --- |
| `pipeline.py` | `KtruPipeline` (реализация `Pipeline`): атрибуты → категории ОКПД2 → кандидаты внутри категорий → сверка характеристик → реранкер для неуверенных → калибровка → топ-3 с пояснениями |
| `category.py` | Ступень 1: топ ОКПД2 по ближайшим соседям среди названий карточек СТЕ (`python -m ml.category` строит модель) |
| `ste_eval.py` | Живой проверочный набор категорий из карточек СТЕ (эталон «<ОКПД2>-X», методика Таира) |
| `extract.py` | `RulesExtractor`: наименование, бренд (словарь + эвристика), модель, характеристики «ключ: значение» |
| `values.py` | Разбор значений КТРУ («≥ 17», «> 2.5 и ≤ 3», «от 8 ГБ») и чисел с единицами из текста позиции |
| `charmatch.py` | Сверка характеристик: match / mismatch / missing, привязка к названию характеристики в тексте |
| `retrieve.py` | `MemoryRetriever`: кандидаты внутри категорий ОКПД2 (+ запасные из всего каталога); TF-IDF по наименованию и по наименованию с характеристиками (или эмбеддер) + нечёткое название + обязательные характеристики; кэш подтверждённых примеров |
| `rerank.py` | none / cross_encoder / llm (Jev через OpenRouter) |
| `calibrate.py` | Калибратор уверенности; `python -m ml.calibrate` обучает на dev |
| `evaluate.py` | Метрики раздела 9 аналитики |
| `synth.py` | Синтетический dev по характеристикам — временная замена ручной разметке |

Главное о данных: внутри одного кода ОКПД2 позиции КТРУ называются одинаково и различаются обязательными числовыми
характеристиками — там решает `charmatch.py`. Но сначала надо попасть в категорию, а по тексту КТРУ это плохо
получается на живых названиях (разбор Таира, 28.10: 40% ОКПД2): медицинские разделы с теми же названиями, случайные
совпадения характеристик. Поэтому схема двухступенчатая: категорию дают карточки СТЕ, где ОКПД2 поставили сами
поставщики, а сверка характеристик выбирает позицию внутри категорий и в чужую категорию не уводит.

## Команды (из корня репозитория)

```bash
python -m pytest ml/tests -q
# модель категорий (данные СТЕ: ste.parquet из dantetemplar/zakupki-dataset, ревизия как в ml/fetch_catalog.py)
python -m ml.ste_eval --ste data/ktru/v2/ste.parquet --catalog data/ktru/v2/catalog_fetched.jsonl --seed 8 --n 1500 \
    --exclude data/ktru/ste/ste_eval_tair.jsonl --out data/ktru/ste/ste_dev.jsonl
python -m ml.category --ste data/ktru/v2/ste.parquet --catalog data/ktru/v2/catalog_fetched.jsonl \
    --exclude data/ktru/ste/ste_eval_tair.jsonl data/ktru/ste/ste_dev.jsonl --out ml/artifacts/category.joblib
KTRU_CATALOG_PATH=data/ktru/v2/catalog_fetched.jsonl python -m ml.calibrate \
    --data data/ktru/v2/eval_samples_v3_dev.jsonl data/ktru/ste/ste_dev.jsonl
KTRU_CATALOG_PATH=data/ktru/v2/catalog_fetched.jsonl python -m ml.evaluate --data data/ktru/v2/eval_samples_v3_dev.jsonl
KTRU_CATALOG_PATH=data/ktru/v2/catalog_fetched.jsonl python -m ml.evaluate --data data/ktru/ste/ste_eval_tair.jsonl \
    [--text-field raw_text_spec]
# test (eval_samples_v3_test.jsonl) — один раз перед сдачей, ничего под него не подбирать
```

Ключи — в `ml/.env` (образец `ml/.env.example`, сам файл в `.gitignore`). `RERANKER=llm` включает Jev через OpenRouter,
ответы кэшируются в `ml/artifacts/llm_cache.jsonl`, повторные прогоны бесплатны.

## Текущие цифры (полный КТРУ: 81 461 позиция, 54 190 для поиска; RERANKER=none, без ключей)

Живые названия — набор Таира (`ste_eval_tair.jsonl`, 1000 карточек СТЕ, 516 кодов ОКПД2, seed 7). Это отложенная
проверка: веса и калибратор подбирались на `ste_dev.jsonl` (seed 8, 1500 карточек, карточки Таира исключены).
Точный код в СТЕ не хранится, поэтому на этих наборах — только ОКПД2.

Скорость — только `classify_batch`, без бэкенда, процесс привязан к 2 ядрам (как в замере Таира); критерий ТЗ < 300 с.
Прежние ~85 с на v3 были на 16 ядрах и с ними не сравнимы. Дольше всего — крупные категории (21.20.23.110 — 9 тыс.
позиций): в предотбор идёт до PREFILTER_MAX позиций, по каждой сверяются обязательные характеристики.

- Модель категорий (`ml/artifacts/category.joblib`, не в git): 106 тыс. названий СТЕ (≤ 150 на код), 1157 кодов ОКПД2,
  66 МБ в памяти, 41 МБ на диске, строится ~90 с. Больше названий на код почти не помогает: 300 — +0,6 п., 1000 — 0.
  Сама по себе на ste_dev угадывает ОКПД2 в 75% (топ-3 — 88%). Без файла модели конвейер ищет по всему каталогу, как раньше.
- Синтетика v3 просела на 2,6 п. top-1: тексты v3 собраны из текста КТРУ, а 19% их кодов ОКПД2 нет среди карточек СТЕ.
  Размен сознательный: на живых строках +28 п. Веса — `retrieve.py` (W_CAT, CAT_POWER, FALLBACK_N), перебор — ниже.
- Перебор на ste_dev / v3 dev (ОКПД2 названия / с характеристиками / v3 top-1): без категорий 40 / 46 / 88,3;
  W_CAT 0,4 — 74 / 75 / 83,1; W_CAT 0,5 и доля² — 71 / 74 / 84,0 (выбрано); доля³ — 66 / 67 / 86,0.
- Калибратор (`ml/models/calibrator.joblib`, в git) обучен на v3 dev и 315 карточках ste_dev, у ОКПД2 которых одна
  позиция КТРУ (там верный ОКПД2 = верный код). ECE на отложенных половинах 0,059–0,068. На живых строках средняя
  уверенность 0,49 при 68% верного ОКПД2 — не завышает (раньше калибратор, обученный на синтетике, завышал).
- Сверка характеристик: совпадение только по единице измерения и «да» из одного упоминания слова («принтер» →
  «Принтер: Да») — слабые свидетельства с весом W_WEAK = 0,3.
- **Бренд на реальных названиях СТЕ** (`python -m ml.eval_brands --data data/ktru/v2/ste_attrs_eval.jsonl`): 83,7%
  со словарём марок `ml/models/brands.txt` (30 тыс. марок из СТЕ). На марках, которых нет в словаре, — 58,9%.
- Загрузка полного каталога ~50 с при старте воркера, модели категорий — ещё несколько секунд.
- **Эмбеддинги** (`EMBEDDER_MODEL=intfloat/multilingual-e5-small`) на старой схеме были хуже TF-IDF и медленнее
  (34 мин на каталог на CPU). По умолчанию выключены.

**Jev (RERANKER=llm) на старом dev:** с весом 0,25–0,75 исправляет и портит поровну, по умолчанию вес 0,05.
Перепроверить на полном каталоге и живых текстах.

## Правила

- Данные (`data/`) не коммитить и не класть в тесты. Каталог КТРУ — открытый датасет ЕИС (жюри разрешило), но данные
  СТЕ (`ste.parquet`, наборы `ste_*.jsonl`, модель категорий) — лицензия датасета не указана, источник zakupki.mos.ru;
  решение за Егором, до него — только локально. `ml/models/brands.txt` тоже из СТЕ — то же решение.
  В тестах — только `contracts/fixtures/` и искусственные строки из `ml/tests/`.
- `eval_test_candidates` и test-разметку не открывать при разработке; пороги и веса — только по dev
  (`eval_samples_v3_dev.jsonl`, `ste_dev.jsonl`). Набор Таира `ste_eval_tair.jsonl` — отложенная проверка, под него не подбирать.
- `ml/` не импортирует FastAPI и Celery.
- Синтетические метрики оптимистичны: веса и калибратор не подбирать на одной синтетике.
- Новая логика — с тестом в `ml/tests/`.
